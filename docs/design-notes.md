# 和设计文档有出入、或者文档没写到的实现选择

[← 回到 README](../README.md)

- **记忆不放进系统提示词。** 模型会校验历史有没有被改写，系统提示词在会话内必须不变。
  所以记忆文件的内容以一条 `<memory>` 消息追加在对话里，只在变化时追加新的一份。
  `AGENT.md` 按会话冻结，原因相同。
- **压缩用服务端的阈值压缩**（输入超过 15 万 token 时触发），摘要要求写在请求里。
- **搜索优先用模型提供方的服务端网页搜索**；提供方没有时由宿主代搜（见 [部署与运维](deploy.md) 的"模型提供方"）。模型代理从搜索结果里
  取出地址记为"见过"；模型自己写在文字里的地址不算。
- **模型代理拒绝会绕过出网代理的服务端工具**：服务端网页抓取（`web_fetch`）、代码执行、MCP 连接器。
  否则电脑可以让 Anthropic 的服务器替它访问任意地址。
- **后台进程在运行结束后失去网络**：出网代理的凭据就是运行通行证，运行结束即失效。
- **基础设施白名单比文档宽一点**：包含 `raw.githubusercontent.com` 等。往这些站点的路径里塞数据，
  理论上是一条低带宽的外泄通道，已列入已知的洞。
- **邮件服务选了 Gmail 的 REST API**：出网代理只懂 HTTP，IMAP/SMTP 用不了。档案是声明式的，
  但 Gmail 发信的正文藏在 base64 编码的 raw 字段里，所以有一小组固定的"提取器"，档案只能按名字引用。
- **长期授权的约束取"全部收件人"**（收件、抄送、密送合起来），不只是收件人：否则授权了给张三发信，
  就能顺手密送给别人。
- **注入检测失败按命中处理**：检测本身出错时，这次运行的长期授权也暂停。
- **验证码识别是规则式的**：同一句话里数字前面不远处有"验证码""code"之类的词。会漏，也会误伤。
- **后台运行的最终文字不发给你**：文档里 `send(text, urgency)` 是一个接口；这里把它做成 `notify` 工具，
  并规定后台运行不调用它就是安静。这样"保持安静"是默认值，而不是 Agent 要刻意做到的事。
- **前置检查在工作进程里做，不在调度器里**：调度器照常把到期事件写进收件箱，工作进程先跑检查，
  "没变化"就把事件标成完成。这样检查脚本和 Agent 运行不会同时在电脑里跑（一台电脑同一时刻一个运行）。
  代价是收件箱里会留下一行"没产生运行"的事件。检查脚本出错（退出码不是 0 或 10）时也叫醒 Agent，让它看到错误、修脚本。
- **通知反馈不单独叫醒 Agent**：文档说反馈"作为事件回到 Agent"。每次点按钮都起一次运行太贵，
  所以反馈只记在发件箱里，出现在之后每次运行的 `<memory>` 里，并汇总进夜间整理的活动概要。
- **夜间整理的"当天概要"由宿主生成**：会话列表、每个会话的第一条事件、运行结果、发出的通知和你的打分。
  细节让 Agent 自己用 recall 去查。整理本身不算活动，所以连续几天没事，它也不会每晚空跑。
- **摘要是定时送的，不是塞进简报里**：文档说摘要项"攒到下一次简报"。简报是 Agent 按你要求设的日程，宿主不知道哪个算简报，
  所以摘要按固定时间（默认 8:00）合成一条送出。
- **Webhook 单独一个端口**：宿主接口（模型代理、会话记录）永远不该暴露到公网，Webhook 却可能需要。
  两者分开，隧道只暴露后者。签名用 HMAC-SHA256；电脑里没有密钥，伪造不了。
- **连接本身记着绑定主机**：文档里 `connection.hosts` 是替身令牌的绑定范围。这里没有档案的连接也能用（默认规则），
  有档案时实际生效的主机是档案和连接的交集。仓库自带档案的服务（Gmail）不需要在连接上写主机。
- **宿主每 5 秒看一眼收件箱表**：你在终端里连接账号时，命令行是另一个进程，直接写库，唤不醒宿主里的等待。
  这只是一次数据库查询，不调用模型，"没有事件就没有运行"不受影响。
- **审阅是消息加命令（或 Telegram 按钮），不是一个网页界面**：文档写的是"审阅界面"。活动视图的网页留到以后。
- **技能列表放在 `<memory>` 里而不是系统提示词里**：系统提示词在会话内不能变，而技能会在会话中途被新建。
- **日程的频率上限按接下来 200 次触发里的最短间隔算**，所以 `*/5 9 * * *` 这种只在一个小时里频繁的也会被拦住。
- **浏览器容器用的是 Playwright 的远程服务，不是完整的配置目录**：`SMRA_BROWSER=docker` 时，宿主经 Playwright 协议
  连到容器里的浏览器，代理通行证由宿主这一侧的 Playwright 应答（Chromium 的 `--proxy-server` 本身不带凭据）。
  这样每次连上都是一个新的浏览器上下文，登录状态靠宿主保存的 Cookie 和本地存储带过去，IndexedDB、Service Worker 不保留。
  默认仍是 `local`，因为 Windows 和 macOS 上没有这套容器网络；放进 microVM 是后续的事。
- **接管是推流截图加点击转发，不是远程桌面**：页面一有变化，宿主就截一张图经 WebSocket 推给你，按网速在三档画质间切换，
  手机确认收到一张才推下一张，网慢时不会越积越多。你点中输入框时手机上先画出框（不等画面），新画面到了框就撤掉。
  你的点击、输入、按键由宿主转给浏览器。够用来登录；看视频、拖拽之类不行。不需要在浏览器那边装 VNC。
- **"Agent 在操作"是一个时间窗口**：从动作开始到页面的网络安静下来（或者等批准的请求超时）。
  窗口外页面自己发的提交一律拦下、不问你，这样统计脚本不会变成审批。代价是窗口内页面恰好发的后台提交也会问你。
- **认请求来历靠浏览器自己填的 `Sec-Fetch-*` 头**：Agent 只能点击和输入，改不了请求头；页面脚本改不了这几个头（浏览器禁止）。
- **被拦下的跳转会自动退回**：提交被挂起等批准时，浏览器会停在代理的拦截页上；代理人把它退回操作前的页面，
  Agent 收到 [审批] 消息后可以直接重做。浏览器的审批在代理上最多挂 120 秒（比普通请求长），你及时批准就不用重做。
  重做时如果页面上有一次性的防伪令牌，请求体变了，会再问你一次。
- **网站档案复用服务档案的格式**：多一个 `type: site`，不写认证和响应过滤，也不能用提取器（浏览器请求没有固定的请求体结构）。
  表单里密码类字段在审批和约束里都只显示被隐藏了。multipart 表单（上传文件）拆不出字段，只能按原始内容给你看。
- **截图检测靠检测模型的视觉能力**：检查的是送进主模型的那张图本身，不做 OCR。和文字检测一样是概率性的，真正的闸门仍是出口规则和你的批准。
- **无障碍树里的密码框值被抹掉**：Playwright 的无障碍树会带出密码框里的值，交给 Agent 之前替换成 `******`。
- **角色说明按会话冻结**：和 `AGENT.md` 一样，角色一节在会话开始时生成、存在会话里，所以系统提示词会话内不变。
  你改了角色文件，下一个新会话生效。`handoff` 工具一直在工具列表里（只有一个角色时调用会报错），工具列表因此不随角色文件变化。
- **"一个任务"按交接链算**：你的一条消息触发的运行是链的源头，它交出去的、再交出去的都记在同一个源头下，花费加在一起。
  审批答复接上的运行算新的源头（那需要你动手，不会自己无限循环）。
- **交接带着"用户在不在等"**：设计文档说交接开目标角色的新会话，没说回复给谁。这里沿用源头运行的前台/后台：
  你发起的事，接手的角色直接回复你；后台事件引发的，接手的角色也是后台，要说话得 `notify`。
- **角色设的日程由它自己处理**：日程到期开的新会话属于设它的角色。跟进本来就回到原会话，自然是同一个角色。
  Webhook 都交给默认角色。夜间整理由默认角色做，顺带整理各角色的记忆目录。
- **跳数上限是"第 6 次交接被拒"**：5 跳意味着最多产生 5 个交接会话。
- **microVM 没有网卡**：文档写的是一块 tap 网卡加宿主侧规则，只放行到两个代理。这里干脆不给网卡：
  客户机代理程序在客户机的 127.0.0.1 上开两个端口（号码和宿主的一样，上层代码不用改），把连接原样转到 vsock；
  宿主在 Firecracker 的 vsock 套接字旁边监听，再转给宿主接口和出网代理。没有路由、没有 DNS，也就不需要防火墙规则去堵，
  不需要 root 去建 tap。代价是电脑里的程序只能用 HTTP 代理出网，和容器实现一样。
- **端口号由宿主在每次启动、恢复后告诉客户机**：宿主重启后端口可能变了，挂起中的虚拟机醒来时照新的开。
- **恢复成功后状态文件立刻删掉**：之后主目录盘会变，旧的内存快照和它对不上。恢复失败就冷启动（后台进程没了，主目录还在）。
- **主目录快照是装着盘镜像的 tar.gz**：在暂停的瞬间拷一份盘（文件系统支持就写时复制），GNU tar 保留稀疏。
  恢复主目录就是换盘、丢掉挂起状态、下次冷启动。
- **保持清醒的请求记在库里**（`host_state` 表）：宿主重启后没到期的接着算，到期或撤销就删掉。
- **孤儿进程**：docker 驱动下电脑容器用 `--init`（docker 自带的 tini 当 1 号进程），Agent 起的后台进程退出后不会留下僵尸。
  这个参数是后来加的，老容器没有：`docker rm -f smra-cell` 后宿主下次用电脑时按新参数重建，主目录在卷里不受影响。
  microVM 的 1 号进程还是 `cell/vm/smra-init` 这个 shell 脚本，不回收孤儿进程，僵尸条目会涨；改它要重建系统盘镜像，还没做。
- **前面各步的测试没有改成"换驱动不改一行全部通过"**：它们直接读写宿主上的主目录文件夹（local 驱动），
  对着 microVM 跑需要一个从宿主读主目录盘的办法。真机上的验收另写在 `test_step9_vm.py`。
