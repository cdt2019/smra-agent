# Personal Agent 设计文档

> 版本：V3.2
> 定位：学习项目，单用户自托管
> 参照：Anthropic《Building always-on agents》、Meta Muse 的安全架构、Grok Bot、Manus Cue、OpenAI Dots、Claude Duet
> 两句话：
> **它不是一个一直在转的进程。它平时睡着，被事件叫醒，跑一小段，存档，再睡。**
> **它醒着的时候整个不可信，包括大脑。不约束它想什么，只在它够得着外界的每个出口设卡。**

---

# 0. 这一版改了什么

V3 把 Agent 写成了隔离区里一个常驻的循环进程，还保留了每 30 分钟一次的心跳。这两处都是上一代自托管 Agent 的做法，这一版全部去掉。

| | V3 | V3.1 |
| --- | --- | --- |
| Agent 的存在形式 | 隔离区里一个常驻进程，阻塞等事 | 没有常驻进程。每个事件触发一次短运行，跑完即退出 |
| 没人找它时 | 每 30 分钟心跳醒一次看看 | 什么都不跑。只有事件和到期的定时器能叫醒它 |
| "过两天看看对方回没回" | 靠心跳碰运气 | Agent 给自己定一个跟进定时器 |
| 事件进入方式 | 直接唤醒 | 一律先进收件箱，按来源去重，连发的合并 |
| 结果怎么到你面前 | 一个带上限的通知调用 | 发件箱加分发器，管节奏和重试 |
| 长任务跨运行 | 靠会话记录 | 每个任务一个进度文件 |
| 记忆整理 | 没有 | 夜间单独的整理运行 |

V3 的出口设计（模型代理、裁决者、替身令牌、服务档案、授权）保持不变。

V3.2 在此基础上补了"电脑"一章（第 5 节）。之前的版本对沙箱只有一份容器加固清单，没有回答用什么隔离、有几层边界、电脑是否跟着 Agent 一起睡。

文档由三部分组成：

| 部分 | 回答的问题 | 章节 | 主要参照 |
| --- | --- | --- | --- |
| 运行周期 | 什么时候醒、什么留下来、结果怎么送达 | 4、6 到 8、14 | Anthropic 那篇文章的五个部件 |
| 电脑 | Agent 在什么里面跑，它睡的时候电脑怎么办 | 5 | Grok Bot 与 Muse 的公开做法、Firecracker |
| 出口 | 醒着的时候够得着什么 | 9 到 13 | Muse 的安全架构 |

那篇文章的五个部件是收件箱、定时器、记忆、权限、发件箱。本文档的"出口"就是其中"权限"一项的展开。

# 1. 产品定义

## 1.1 它是什么

一个只为你工作的 Agent。它有自己的电脑、跨运行的记忆、你授权的外部账号。你发消息、外部系统有动静、它自己定的时间到了，它就醒来处理，然后把结果发给你或者保持安静。它能自己学会新本事，也可以分成几个角色。

## 1.2 必须跑通的场景

| 编号 | 场景 | 考验什么 | 步骤 |
| --- | --- | --- | --- |
| S1 | "把这份 CSV 分析一下，出个带图的报告" | 运行、电脑、文件往返 | 2 |
| S2 | 三天后："上次那个报告，第二张图换成按月的" | 记忆、进度文件 | 2 |
| S3 | "调研这三家竞品，写成文档" | 公网出口规则 | 3 |
| S4 | "回一下张三，说周四可以" | 替身令牌、服务档案、延迟审批 | 4 |
| S5 | 发完后它自己定了个跟进：两天后张三没回，它提醒你 | 跟进定时器 | 5 |
| S6 | 每天早上 8 点收到简报；连续三条消息只触发一次处理 | 日程、合并、发件节奏 | 5 |
| S7 | 工单系统来了一条新工单，它看完决定不打扰你 | 事件触发、"保持安静"也是一种结果 | 5 |
| S8 | "我们用的那个工单系统，你接一下" | 自写连接器 | 6 |
| S9 | "去这个没有接口的网站查一下我的订单状态" | 浏览器 | 7 |
| S10 | "让研究员去查资料，让秘书整理成邮件草稿" | 多角色交接 | 8 |
| S11 | 把 Agent 的代码替换成一个恶意程序，让它尽力窃取凭证、外泄文件、冒名发信 | 出口是否守得住 | 3 起每步都测 |
| S12 | 电脑空闲后挂起，不占内存和 CPU；新事件到来时恢复，之前起的后台进程还在 | microVM、挂起与恢复 | 9 |

## 1.3 非目标

- 多用户、多租户、多台机器、高可用。
- 支付。架构为它留了位置，但不做。
- 语音和电话。
- 内核层的数据流追踪。
- 多个运行同时进行。

# 2. 核心思想与决策

## 2.1 两组原则

**关于运行周期：**

1. 没有事件就没有运行。不轮询，不空转。
2. 事件来源不直接调用 Agent，一律先写入收件箱。
3. 每次运行都假设自己随时会被打断。要留下来的东西，在运行中就写进记忆或进度文件。

**关于出口：**

4. 假设隔离区始终已被完全攻破。
5. 隔离区里什么真东西都没有：没有模型密钥，没有真凭证，没有浏览器登录态。
6. 出口是有限的、可枚举的，每个出口由隔离区外的代码把守，依据是实际发出的字节。

## 2.2 决策表

| 编号 | 决策 | 结论 | 放弃的方案及原因 |
| --- | --- | --- | --- |
| D1 | 存在形式 | 按事件启动的短运行 | 常驻进程：上下文迟早装不下，崩溃丢状态，空转花钱 |
| D2 | 唤醒来源 | 只有收件箱里的事件 | 心跳轮询：大多数醒来无事可做，真正的时机又对不上 |
| D3 | 时间驱动 | 定时器单独存放，到期后变成收件箱事件 | 定时器直接启动运行：会和别的运行撞车 |
| D4 | 并发 | 一个收件箱，一个工作进程，同一时刻一个运行 | 并发运行：同一台电脑上互相踩文件，记忆互相覆盖 |
| D5 | 运行代码放哪 | 隔离区内 | 放可信侧：被注入后，它持有的权限全部失守 |
| D6 | 权限裁决 | 隔离区外的独立裁决者，看解密后的实际请求 | Agent 自查：被裁决者和裁决者是同一个 |
| D7 | 凭证 | 替身令牌，出口处、目的地匹配时才换成真凭证 | 发短期真令牌：仍可被带到别处使用 |
| D8 | 染污追踪 | 不做，直接假设始终已攻破 | 按运行标记：先存成文件、下次运行再外泄即可绕过 |
| D9 | 公网访问 | 搜索放行；宿主见过的链接放行；自己拼的地址要审批 | 全开或全关 |
| D10 | 等待审批 | 运行结束，会话停在那个调用上；答复作为新事件回来 | 运行挂着等：占着唯一的工作进程 |
| D11 | 审批通道 | 裁决者生成，走发件箱，结果直达裁决者 | 走 Agent 的回复：可伪造、可代答 |
| D12 | 对外发消息 | 一律经发件箱，由分发器决定何时送达 | 直接发：无法控制打扰，失败无法重试 |
| D13 | 记忆 | 文件；只存查不回来的东西 | 把查得到的也抄一份：会过期，还占上下文 |
| D14 | 多角色 | 共用收件箱、电脑和授权；各有记忆 | 每个角色一套权限：同一隔离区内是假边界 |
| D15 | 隔离技术 | 上层只依赖一个驱动接口；先用容器实现，再用 microVM 实现 | 一开始就上 microVM：前面几步会被环境问题卡住 |
| D16 | 边界层数 | 一层：电脑的边界就是 Agent 与把守者之间的边界，把守者在宿主上 | 两层（外层虚拟机加内层运行区）：那是多租户托管的需要 |
| D17 | 电脑是否休眠 | 运行结束后空闲一段时间即挂起，事件到来时恢复 | 一直开着：空闲占资源；每次工具调用后就拆：反复恢复的总成本更高 |

# 3. 架构

``` text

      |                |                    调度器（每分钟看一次到期的）
      v                v                        v
 +----+----------------+------------------------+------- 宿主侧（可信）------+

 |                          |                                              |

 |                          |                 ^                            |

 |      ^              ^        \                                          |
 |      |              |         凭证服务 / 授权库 / 服务档案                |
```

# 4. 运行周期

## 4.1 基本概念

| 概念 | 定义 |
| --- | --- |
| 事件 | 一件需要 Agent 处理的事：你的消息、审批答复、Webhook、到期的定时器、角色间的交接 |
| 运行 | Agent 被叫醒一次：收到事件、干活、存档、退出。通常几秒到几分钟 |
| 会话 | 一段消息和工具调用的记录。一次运行发生在一个会话里；后续运行可以接着同一个会话 |
| 电脑 | 隔离区和主目录。文件一直在；没有运行时里面没有 Agent 在跑，空闲久了整台挂起（第 5 节） |

## 4.2 一次运行

宿主侧的工作进程：

``` python
def worker():
    while True:
        events = inbox.claim_batch()            # 没有事件时阻塞在这里，不调用模型
        session = route(events)                 # 接着旧会话，还是开新会话（4.4）
        run = runs.start(session, events)
        computer.ensure_awake()                 # 挂起着就先恢复（第 5 节）
        outcome = cell.exec("agent-run", run.id, timeout=run.limit)
        runs.finish(run, outcome)
        inbox.mark_done(events)
```

这里的 `while True` 是队列消费者。它绝大部分时间阻塞在第一行。

隔离区里被启动的程序：

``` python
def main(run_id):
    ctx = host.run_context(run_id)      # 会话记录、本次的事件、最近发给你的消息
    ctx = load_memory() + ctx           # 第 8 节
    while True:
        resp = model(ctx)               # 发往模型代理
        host.log_append(resp)
        if not resp.tool_calls:
            break
        for call in resp.tool_calls:
            result = execute(call)      # 本地子进程，没有权限判断
            host.log_append(call, result)
        if host.should_yield(run_id):   # 你的消息到了，而这是一次后台运行
            break
    # 进程退出
```

内层的"调模型、执行工具、再调模型"和任何 Agent 都一样。这段代码里没有权限判断：工具想发请求就直接发，能不能成由出口决定。把它换成任何现成的 Agent 框架，安全性不变。

这段代码只读挂载进隔离区，Agent 改不了。

## 4.3 运行的四种结束

| 结束方式 | 含义 | 之后 |
| --- | --- | --- |
| 发了消息 | 往发件箱写了内容 | 分发器决定何时送达 |
| 保持安静 | 判断不值得打扰你 | 什么都不发生。这是正常且常见的结果 |
| 延迟 | 某个出站请求需要你批准 | 会话存档停在那个调用上；你的答复作为新事件回来（11.5） |
| 让路 | 后台运行期间你发来了消息 | 原事件放回收件箱，稍后在同一会话里继续 |

外加两种异常：超时被工作进程杀掉，或进程崩溃。两者都把事件放回收件箱重试，最多 3 次，之后标记失败并告诉你。

## 4.4 事件进哪个会话

| 事件 | 会话 |
| --- | --- |
| 你的消息 | 当前对话会话。你发 `/new` 或对话空闲超过 6 小时后开新的 |
| 审批答复 | 发起那个审批的会话 |
| 跟进定时器 | 设定它的那个会话 |
| 日程定时器 | 每次都开新会话 |
| Webhook | 带关联键的（如工单号）进同一会话；否则开新会话 |
| 角色交接 | 目标角色的新会话 |

新会话只包含固定开销和触发事件。接续旧会话则带回之前的记录。

## 4.5 运行在哪里

运行发生在"电脑"里。电脑是一个隔离环境，里面的一切都当作可能被对手控制。它用什么技术隔离、怎么联网、什么时候睡，见第 5 节。

电脑里可以留有后台进程（比如一个跑了一半的长脚本）。它们跨运行存活，但它们不是 Agent，调不了模型，也受同样的出口约束。

# 5. 电脑

## 5.1 这一章回答什么

| 问题 | 结论 | 小节 |
| --- | --- | --- |
| 用什么技术隔离 | 驱动接口之下可换；先容器，后 microVM | 5.2、5.4 |
| 有几层边界，把守者放在哪 | 一层；把守者在宿主上 | 5.3 |
| Agent 睡的时候电脑怎么办 | 空闲后挂起，事件到来时恢复 | 5.5 |
| 文件放在哪，怎么做快照 | 主目录是独立的持久盘 | 5.6 |
| 怎么联网 | 只有通向三个出口的路 | 5.7 |
| 多个角色共用还是各用各的 | 共用一台；浏览器另算 | 5.9 |

## 5.2 三档隔离技术

| | 容器 | gVisor | microVM |
| --- | --- | --- | --- |
| 隔离靠什么 | 命名空间、cgroup、系统调用过滤 | 用户态内核拦截系统调用 | 硬件虚拟化，独立的客户机内核 |
| 和宿主共享内核 | 是 | 否，但拦截层自身是攻击面 | 否 |
| 一个内核漏洞的后果 | 可能逃到宿主 | 需先攻破拦截层 | 需再攻破虚拟机监视器 |
| 启动 | 最快 | 快 | 冷启动百毫秒级 |
| 连内存一起挂起和恢复 | 不成熟 | 本文档不用 | 原生支持 |
| 兼容性 | 最好 | 少数系统调用不支持 | 好，就是一台完整的 Linux |
| 运行要求 | 任何有 Docker 的机器 | Linux 宿主 | Linux 宿主，且有 KVM |

这一代托管产品在用户之间的边界上都选了虚拟机一档。Grok Bot 的官方文档写明每个用户一台常驻的 Firecracker microVM，有自己的内核、内存和虚拟设备。Muse 是每个用户一台专属虚拟机。

对本项目，microVM 值得做的理由有两个，按重要性排序：

1. **挂起和恢复**。它能把内存和设备状态存成文件、进程退出、之后原样恢复。这正好对上"Agent 大部分时间在睡"的运行模型。容器做不好这件事。
2. **边界更强**。第 2 节假设电脑里的代码完全受对手控制。在容器里这意味着对手和宿主内核之间只隔着系统调用过滤；在 microVM 里还隔着一个客户机内核和一个很小的虚拟机监视器。

## 5.3 几层边界

需要区分两种边界：

| 边界 | 隔开谁和谁 | 强度要求 |
| --- | --- | --- |
| 外层 | 一个用户的电脑和宿主、和别的用户 | 高，要挡住内核级攻击 |
| 内层 | Agent 和把守它的服务（裁决者、凭证服务） | 要保证 Agent 碰不到真凭证、绕不过出口 |

Muse 两层都有：外层是每用户一台虚拟机，内层是虚拟机里用 systemd-nspawn 隔出的运行区，把守服务放在虚拟机内、运行区外。这样做是因为它是多租户托管服务，希望每个用户的数据和凭证都留在该用户自己的虚拟机里，不进入中心基础设施。

本项目只有一个用户，宿主就是你自己的机器。所以把两层合成一层：

``` text
宿主：把守者（模型代理、出网代理、裁决者、凭证服务、宿主接口）
  |
  |  唯一的边界
  v
电脑：Agent 的一次次运行、主目录、工具、后台进程
```

把守者在宿主上，电脑里只有不可信的东西。用容器实现时这道边界是容器的边界，用 microVM 实现时是虚拟机的边界。上层设计不变，变的只是这道边界有多硬。

代价是宿主成了唯一的可信基座，宿主被攻破则全盘失守。对自托管单用户，这是可以接受的前提。

## 5.4 驱动接口

宿主侧只通过这个接口使用电脑，不关心底下是什么。

``` python
class Computer(Protocol):
    def state(self) -> State: ...                 # ABSENT / RUNNING / SUSPENDED
    def create(self, spec: Spec) -> None: ...     # 准备镜像、主目录盘、网络
    def start(self) -> None: ...                  # 冷启动
    def exec(self, argv, env, timeout) -> Exec: ...   # 起一个进程，流式取输出和退出码
    def suspend(self) -> None: ...                # 存下状态，释放宿主资源
    def resume(self) -> None: ...                 # 从挂起处继续
    def ensure_awake(self) -> None: ...           # 按当前状态调用 start 或 resume
    def snapshot_home(self, label) -> Ref: ...    # 主目录快照
    def restore_home(self, ref) -> None: ...
    def destroy(self) -> None: ...
```

两个实现的对照：

| 方法 | 容器实现 | microVM 实现 |
| --- | --- | --- |
| `create` | 建容器、数据卷、内部网络 | 准备内核、根文件系统镜像、主目录盘镜像、tap 设备 |
| `start` | 启动容器 | 经监禁程序启动虚拟机监视器，引导客户机 |
| `exec` | 容器运行时的执行接口 | 客户机里的代理程序，经 vsock 接收命令 |
| `suspend` | 冻结容器内全部进程。CPU 归零，内存仍占着 | 暂停客户机，把内存和设备状态写成文件，退出监视器进程。CPU 和内存都归零 |
| `resume` | 解冻 | 起一个新的监视器进程，加载状态文件，继续执行 |
| `snapshot_home` | 对数据卷打包 | 在挂起或暂停的瞬间对主目录盘镜像做写时复制的拷贝 |

容器实现的 `suspend` 是打了折扣的：能停 CPU，停不了内存占用。这是它作为过渡实现可以接受的地方，也是后面要换掉它的原因。

microVM 实现里的"客户机代理程序"是一个很小的常驻程序，在电脑里监听 vsock，负责起进程、传输出、报告状态。它在不可信的一侧，只是执行者，被攻破也不增加对手的能力。

## 5.5 休眠与唤醒

``` text
            事件到来，工作进程调用 ensure_awake
   ABSENT ---------------------------------------> RUNNING
                                                    |   ^
                        运行结束后空闲 10 分钟，     |   |  事件到来
                        且没有有效的保持清醒请求      v   |
                                                  SUSPENDED
```

规则：

- **何时挂起**：最后一次运行结束后空闲 10 分钟。不在每次工具调用后挂起，也不在每次运行后立刻挂起。有研究测过：每次工具调用后就拆掉沙箱，沙箱本身的成本降了 65%，但反复做快照恢复使总成本升到常驻方案的 4.9 倍。
- **何时恢复**：工作进程要启动运行时，或调度器要执行前置检查脚本时。
- **谁来决定**：宿主。电脑自己不能决定不睡。

**后台进程怎么办**。挂起会冻住电脑里的一切，包括一个正在跑的两小时脚本。所以提供一个宿主接口调用 `keep_awake(reason, until)`：

- Agent 起长任务前调用它，说明原因和预计结束时间。
- 上限由宿主执行，默认最长 4 小时，到点后照常挂起。
- 配套的做法是 Agent 同时给自己设一个跟进定时器，到时候醒来看结果。

**恢复之后有三件事不一样**，系统提示词里要告诉 Agent：

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 时钟跳变 | 客户机的时间停在了挂起那一刻 | 恢复后由客户机代理程序立刻对时 |
| 网络连接失效 | 挂起期间对端早已超时 | 后台进程要能重连；长下载用可续传的方式 |
| 只读的系统部分可能已更新 | 见 5.6 | 装在主目录之外的东西不保证还在 |

**状态文件里有什么**。挂起时写出的文件包含电脑的全部内存。这在一般系统里是敏感的，因为内存里会有密钥。在本设计里，电脑内存中本来就没有任何真凭证，只有替身令牌，所以状态文件泄露的后果和主目录泄露相当。这是"电脑里什么真东西都没有"这条原则的一个附带好处。

状态文件的大小约等于分配给电脑的内存，所以内存不要给太多，默认 2 GB。

## 5.6 存储

电脑挂三块盘：

| 盘 | 内容 | 读写 | 生命周期 |
| --- | --- | --- | --- |
| 系统盘 | 操作系统、预装的 Python、Node、git、代理根证书 | 只读，上面叠一层临时可写层 | 随镜像版本更新；可写层在冷启动时清空 |
| 主目录盘 | `/home/agent` 的全部内容 | 读写 | 永久 |
| 核心盘 | `core/AGENT.md` 和运行程序 | 只读 | 由宿主管理 |

这样分的好处：

- 升级系统镜像不碰主目录。
- 主目录盘的大小就是磁盘配额，是硬上限。
- Agent 用包管理器装到系统路径的东西在冷启动后会消失，装到主目录下的会留着。这一点要在系统提示词里说明。

主目录每小时做一次快照，历史保存在宿主侧，电脑碰不到。夜间整理之前额外做一次。"重置"就是把主目录恢复到某个快照并冷启动。

## 5.7 网络

电脑只有一块网卡，另一端在宿主上。宿主对这块网卡的规则是：

- 只接受目的地为出网代理和模型代理的连接，其余全部丢弃。
- 不做转发，不做地址转换。电脑没有通往外部的路由。
- 电脑里没有 DNS，域名由代理解析。
- 只有 HTTP 和 HTTPS 能出去，git 只能走 HTTPS。

宿主接口不走网络。microVM 实现里它走 vsock，容器实现里是一个挂进去的本地套接字。这样电脑无法通过扫描网络发现宿主上的其他服务。

## 5.8 加固

**容器实现**：

- 非 root 运行，丢弃全部 capabilities，禁止提权。
- 根文件系统只读；可写的只有主目录和有上限的临时目录。
- 内存、CPU、进程数上限。
- 不挂载容器运行时的控制套接字和任何宿主机路径。
- 有 Linux 宿主时把运行时换成 gVisor，是一行配置的改动。

**microVM 实现**：

- 虚拟机监视器经它自带的监禁程序启动：独立的非特权用户、独立的根目录、cgroup 限制、系统调用过滤。
- 虚拟设备只给必需的：一块网卡、三块盘、vsock。
- 虚拟 CPU 数和内存在启动时固定。
- 客户机内核和监视器本身要跟着上游更新。

在 microVM 实现里，电脑内部的 Agent 可以是 root。边界在虚拟机上，不在客户机的用户权限上。对抗测试因此可以更狠：给恶意脚本客户机里的 root，出口仍然要守得住。

## 5.9 共用还是各用各的

- **角色之间共用一台电脑**。和第 17 节一致：角色不是安全边界，分开只是为了上下文和记忆。Grok Bot 也是同一用户的所有 Bot 共用一台。
- **浏览器是另一台**。它里面有登录态，必须和 Agent 的电脑隔开（第 16 节）。它可以先用容器，之后同样换成 microVM。
- 将来需要权限不同或并行的角色时，再给它单独的电脑和单独的收件箱。

## 5.10 学习项目的取舍

- 第 1 步就把驱动接口定下来，用容器实现。前八步的上层代码都只依赖接口。
- microVM 实现单独作为第 9 步。它只换驱动，不动上层，所以可以在第 5 步之后的任何时候做。
- microVM 需要一台有 KVM 的 Linux 机器。在 Windows 上要靠 WSL2 的嵌套虚拟化，这一点没有验证过；备选是一台支持嵌套虚拟化的 Linux 主机。
- 做的时候要量四个数：冷启动耗时、恢复耗时、状态文件大小、挂起后宿主的内存占用。它们决定 5.5 里"空闲 10 分钟"这个数该不该调。

# 6. 收件箱

## 6.1 为什么事件来源不直接调 Agent

- 两个事件同时到，会启动两个互相竞争的运行。
- 处理到一半崩溃，事件就丢了。

所以所有来源只做一件事：往收件箱写一行。

## 6.2 三个部分

| 部分 | 是什么 | 做什么 |
| --- | --- | --- |
| 持久列表 | 数据库里的一张表 | 事实来源。每个事件有状态：待处理、处理中、完成、失败 |
| 接收端 | 一个 HTTP 接口，加渠道的消息回调 | 校验签名、写入、立刻应答。不做任何耗时的事 |
| 工作进程 | 一个后台进程，全局唯一 | 取事件、合并、启动运行 |

## 6.3 规则

- **去重**：每个事件带来源和来源标识（消息平台的消息号、Webhook 的投递号、定时器号加到期时间）。两者组合唯一，重复投递直接忽略。
- **合并**：工作进程取事件时，把同一会话里所有待处理的事件一起取出，交给一次运行。你连发三条消息，Agent 只醒一次，看到的是三条。
- **优先级**：你的消息 > 审批答复 > 角色交接 > Webhook > 定时器。
- **崩溃恢复**：工作进程启动时，把"处理中"但没有对应活跃运行的事件改回"待处理"。
- **接收端不做深度检查**：注入检测之类的事留到运行中由模型代理去做（第 10 节），接收端只管快进快出。

## 6.4 运行中来了新事件

| 新事件 | 当前运行 | 处理 |
| --- | --- | --- |
| 你的消息 | 就是你这个对话的运行 | 并入当前运行，在下一步之前进入上下文 |
| 你的消息 | 一次后台运行 | 后台运行让路，先处理你的 |
| 其他 | 任意 | 留在收件箱，等下一次运行 |

# 7. 定时器

## 7.1 两种

| | 跟进 | 日程 |
| --- | --- | --- |
| 谁设的 | Agent 在运行中给自己设 | 你设，或 Agent 应你的要求设 |
| 次数 | 一次 | 按周期重复 |
| 例子 | "两天后看张三回了没" | "每天 8 点发简报" |
| 到期后 | 标记完成 | 推进到下一次 |
| 进哪个会话 | 设定它的会话 | 新会话 |

跟进是这一版最重要的新增。它让 Agent 能说"这件事现在做不完，我到时候再来看"，然后真的回来。之前的版本没有这个能力，只能指望一个定期醒来的轮询碰巧想起来。

设跟进时 Agent 要写清楚到时候做什么、判断依据是什么，因为醒来的那次运行不一定还带着完整的上下文。

## 7.2 调度器

定时器存在自己的表里，和收件箱分开：收件箱只放"现在就该处理"的事，定时器库放"以后才该处理"的事。

调度器是一个每分钟执行一次的函数：

``` python
def tick(now):
    for t in timers.due(now):
        if t.precheck and not run_precheck(t):     # 7.3
            advance_or_finish(t); continue
        inbox.add(source="timer", source_id=f"{t.id}:{t.due_at}", payload=t.payload,
                  session=t.session if t.kind == "follow_up" else None)
        advance_or_finish(t)                       # 跟进标记完成；日程算出下一次
```

- 定时器不直接启动运行，只往收件箱放事件。这样它和别的事件一起排队、去重、合并。
- 宿主停机期间错过的日程，启动后每个最多补一次。错过的跟进全部补上。

## 7.3 前置检查

有些日程是"条件满足才值得叫醒 Agent"，比如盯一个页面的价格。这类日程可以带一个前置检查脚本：

- 脚本放在隔离区里，由调度器触发执行，不经过模型。
- 它同样受出口约束，可以用替身令牌查接口、取页面算哈希。
- 退出码表示"有变化"或"无变化"。无变化就不产生事件。

这样一个每 15 分钟检查一次的盯价任务，在价格没变的日子里一次模型调用都不产生。

## 7.4 上限

由宿主执行，Agent 绕不过去：

- 定时器总数上限（默认 50）。
- 日程的最高频率（默认每 15 分钟）。
- 跟进最早只能设在 1 分钟之后。
- 每个新定时器都记入活动视图；日程的创建会告诉你。

# 8. 记忆

## 8.1 原则

**只存查不回来的东西。** 凡是在别的系统里查得到的（工单内容、邮件原文、日历），只存一个指针，用的时候去查。抄下来的副本会过期，而且每次都占上下文。

## 8.2 布局

``` text
/home/agent/
  core/
    AGENT.md               身份、语气、底线。只读，只有你能改
  memory/
    instructions.md        你给的长期指令。每次运行加载
    index.md               笔记索引，每条一行。每次运行加载
    notes/                 具体笔记。按需读取
      people.md
      preferences.md
    progress/              每个进行中的任务一个文件。按需读取
      q4-report.md
  skills/                  技能
  tools/                   自写的连接器和小工具
  inbox/                   你发来的文件
  work/                    工作文件
  roles/<name>/memory/     各角色自己的记忆（第 17 节）
```

| 种类 | 内容 | 何时进上下文 |
| --- | --- | --- |
| 你的指令 | "给客户的邮件都抄送小李""周末别打扰我" | 每次运行 |
| 关于你的笔记 | 角色、偏好、被你纠正过的地方 | 索引每次加载，正文按需 |
| 任务进度 | 做完了什么、还剩什么、卡在哪、相关文件和指针 | 接着做这个任务时 |
| 已经告诉过你的 | 最近发给你的消息 | 每次运行，由宿主提供 |

最后一项不让 Agent 自己记。工作进程在启动运行时，从发件箱取最近 10 条已送达的消息放进上下文。发件箱的记录是宿主自己写的，比 Agent 自己维护的文件可靠。它的作用是避免重复汇报同一件事。

## 8.3 进度文件

长任务不可能在一次运行里做完，也不应该指望会话记录撑到最后。约定是：

- 开始一个预计要跨运行的任务时，先建进度文件。
- 每完成一个阶段就更新它，而不是等到运行结束。
- 设跟进定时器时，在载荷里写上进度文件的路径。
- 任务结束后把值得长期保留的结论并入笔记，删掉进度文件。

这样即使会话被压缩、被换新、运行被杀掉，下一次运行读一个文件就能接上。

## 8.4 上下文

每次运行开头的固定开销：系统提示词与 `core/AGENT.md`、工具定义、`instructions.md`、`index.md`。这部分要保持精简，并且顺序固定以利用提示词缓存。之后是会话记录、最近发给你的消息、本次的事件。

会话太长时有两个办法：压缩较早的消息，或者开一个新会话。两者都会丢细节，所以在此之前要先把要紧的东西写进进度文件或笔记。对跨天的任务，优先开新会话加进度文件。

## 8.5 夜间整理

每晚一次的内置日程，用一次专门的运行回顾当天的会话记录，做四件事：

- 合并重复的笔记，替换过时的条目。
- 找出只有跨多次运行才看得出的规律，例如你连续三次把简报里的某一栏删掉了。
- 清理已完成任务的进度文件。
- 把反复出现的做法提议为技能。

它是一次普通的运行，面对同样的出口。整理前宿主先给主目录做快照，整理结果的摘要进入第二天的简报。

## 8.6 记忆被污染怎么办

不阻止。既然假设隔离区随时可能被攻破，记忆被污染只是其中一种形式，后果同样被出口兜住。能做的是看得见、退得回：

- 宿主每小时对主目录做快照，历史存在宿主侧，隔离区碰不到。
- 活动视图里可以查看记忆的每次改动并回滚。
- "重置"：恢复到某个快照，同时撤销所有长期授权和 Agent 自己设的定时器。

# 9. 权限：三个出口

一次运行使用的是你的权限，而且没人看着。这是整个系统风险最高的部分。

穿过隔离区边界的线只有三条：

| 出口 | 通向 | 把守者 | 守什么 |
| --- | --- | --- | --- |
| 模型 | 模型提供方 | 模型代理 | 模型密钥、花费、注入检测 |
| 网络 | 互联网与外部服务 | 出网代理加裁决者 | 外泄、冒名操作、内网探测 |
| 宿主接口 | 会话记录、定时器、发件箱、浏览器 | 宿主进程 | 历史不可改、数量上限、打扰节奏 |

对每个出站动作，结果是三选一：放行、拒绝、等你批准。

---

# 10. 出口一：模型代理

隔离区把模型代理当成模型接口来调，请求里不带密钥。代理做四件事：

1. **加密钥**。只转发到配置好的模型提供方。
2. **管花费**。工作进程启动运行时向代理登记运行号和预算；代理按运行、按天计数，超限即拒绝。
3. **留底**。每次请求和响应原样记入宿主日志。Agent 自己上报的记录可能造假，这份不会。
4. **注入检测**。对请求里新出现的工具结果和事件内容，用一个便宜的分类模型判断"是否包含针对 AI 的指令"。命中后，本次运行内暂停所有长期授权，并在发件箱里放一条提示。

第 4 条是概率性的。它的作用是减少长期授权被滥用的机会，整个设计不依赖它。

# 11. 出口二：网络与裁决者

## 11.1 流程

``` text
隔离区发出请求
      |
      v
出网代理：解密，得到 方法 / 主机 / 路径 / 头 / 请求体
      |
      v
基础检查：目的 IP 是否内网、环回、宿主（代理自己解析并连接，无重绑定空隙）
      |
      v
裁决者：
   1. 归类：哪个服务的哪个动作（查服务档案）
   2. 查授权库：有没有覆盖它的有效授权
   3. 按默认策略判定
      |
      +-- 放行 --> 换上真凭证（如有）--> 发出 --> 响应过滤 --> 返回
      +-- 拒绝 --> 返回 403 和原因
      +-- 询问 --> 生成审批请求（11.5）
```

## 11.2 三类目的地

| 目的地 | 判断方式 | 默认策略 |
| --- | --- | --- |
| 已连接的服务 | 请求带替身令牌，且主机在该连接的绑定列表里 | 按服务档案 |
| 基础设施白名单 | 包管理源、代码托管的只读地址 | 只放行 GET |
| 公网 | 其余全部 | 按公网规则 |

## 11.3 服务档案

一份声明式的数据，告诉裁决者某个服务的请求该怎么归类、怎么向你描述。

``` yaml
service: github
hosts: [api.github.com]
auth: { header: Authorization, scheme: Bearer }

actions:
  - match: { method: GET, path: "/**" }
    class: read

  - match: { method: POST, path: "/repos/{owner}/{repo}/issues/{n}/comments" }
    class: send
    summary: "在 {owner}/{repo}#{n} 发表评论"
    show: [body.body]
    constraint_keys: [owner, repo]

  - match: { method: POST, path: "/repos/{owner}/{repo}/pulls" }
    class: write
    summary: "在 {owner}/{repo} 开 PR：{body.title}"
    constraint_keys: [owner, repo]

  - match: { method: PUT, path: "/repos/{owner}/{repo}/pulls/{n}/merge" }
    class: irreversible
    summary: "合并 {owner}/{repo} 的 PR #{n}"

  - match: { method: DELETE, path: "/**" }
    class: irreversible

response_filters: []
```

| 类别 | 含义 | 无授权时 | 可授予的最大范围 |
| --- | --- | --- | --- |
| `read` | 读取 | 放行 | — |
| `write` | 写，只影响你自己、可撤销 | 询问 | 永久 |
| `send` | 他人可见 | 询问 | 永久，但必须带约束 |
| `irreversible` | 删除、合并等 | 询问 | 仅一次 |
| `money` | 涉及资金 | 询问 | 仅一次 |

没有匹配到任何规则的请求：GET 和 HEAD 按 `read`，其余按 `irreversible`，并展示原始请求。

**响应过滤**。邮件服务的档案默认启用一条：把验证码、密码重置链接、免密登录链接从正文里抹掉。否则"能读邮箱"等于"能接管绑定了这个邮箱的所有账号"。

## 11.4 公网规则

被攻破的 Agent 可以把数据拼进地址发出去，又不能全关，否则无法调研。

| 请求 | 判定 |
| --- | --- |
| 调用搜索服务 | 放行。搜索服务作为一个已连接服务接入 |
| GET，且这个地址宿主"见过" | 放行。去掉 Cookie 和多余的头 |
| GET，地址是 Agent 自己拼的 | 询问。可按域名授权 |
| 非 GET | 询问，展示解码后的请求体 |

"见过的地址"指这个完整的地址字符串曾出现在经过代理的某个响应里。代理在返回响应时提取其中的链接存入集合。

效果：搜索、点开结果、顺着链接读下去，畅通无阻；把通讯录编码进查询参数发出去会被拦下，因为没有任何页面给过它那个地址。

## 11.5 授权与延迟审批

**授权是一张能力凭据**：服务与动作、约束、范围、来源。

| 范围 | 何时失效 |
| --- | --- |
| 一次 | 用掉即失效，且绑定这个请求的哈希 |
| 本次运行 | 当前运行结束 |
| 本次会话 | 会话结束 |
| 限时 | 到点 |
| 永久 | 你撤销 |

裁决者根据动作类别决定给你哪几个范围可选。

**延迟审批的流程**：

1. 裁决者生成审批请求，内容来自服务档案的摘要模板和解码后的请求字段，不来自 Agent。例如："发送邮件。收件人：zhangsan@example.com。主题：Re: 周四。正文：……"。
2. 请求里若带 `X-Purpose` 头，作为"Agent 自述的目的"单独显示并标明不可信。
3. 审批请求进入发件箱，作为一种独立的消息类型带按钮送达。
4. 代理把出站请求挂起最多 30 秒。你正好在线并批了，就直接放行。
5. 否则代理返回 403 和审批号。Agent 的程序看到后结束本次运行，结束方式为"延迟"。会话记录停在这个工具调用上。工作进程腾出来处理别的事件。
6. 你点了按钮。宿主把答复直接交给裁决者生成授权，同时往收件箱放一条"审批已答复"事件。
7. 这个事件触发一次新运行，接着原会话，重试那个请求，这次能匹配上授权。
8. 24 小时未处理按拒绝，同样产生一条事件让 Agent 知道。

"一次"的授权绑定请求哈希。重试时请求体变了就会再问一次，这是有意的，否则可以批准后改内容。

# 12. 凭证

``` text
你在宿主界面连接账号
      |
      v
凭证服务：加密保存真凭证，生成替身令牌 sur_github_9f2c...
      |
      v
隔离区只拿到替身令牌
      |
      v
隔离区里任何程序带着替身令牌发请求
      |
      v
出网代理：识别替身 --> 查绑定主机 --> 目的地匹配且裁决放行 --> 换成真凭证
```

三条硬规则：

1. **绑定主机**。替身令牌只在目的地属于该连接的主机列表时才被替换。发到别处，对方收到的是一串无用的字符。这是整个机制里最不能出错的一行判断。
2. **真凭证不回流**。响应体里若出现真凭证的值，抹掉。
3. **刷新在宿主侧**。OAuth 刷新由凭证服务完成。

好处是隔离区里的任何代码都能直接调接口：curl、现成的 SDK、Agent 自己写的脚本。不需要在可信侧为每个服务手写连接器。

真凭证加密存在宿主的数据库里，密钥来自环境变量或系统钥匙串。

# 14. 发件箱

## 14.1 为什么需要

常驻 Agent 在后台干活。你看到的不是它一步步的过程，而是结果。所以"怎么把结果送到你面前"是一个独立的问题：发多少、什么时候发、发失败了怎么办。

## 14.2 结构

发件箱是一张待发消息的表，加一个分发器。分发器之于发件箱，相当于工作进程之于收件箱。

| 消息类型 | 谁写入 | 送达时机 |
| --- | --- | --- |
| 回复 | 由你的消息触发的运行 | 立刻 |
| 即时通知 | 后台运行，`urgency=now` | 立刻，受每日上限和安静时段约束 |
| 摘要项 | 后台运行，`urgency=digest` | 攒到下一次简报 |
| 审批请求 | 裁决者 | 立刻，不受上限约束 |

分发器的职责：

- **节奏**：即时通知每日上限默认 3 条，超出降为摘要项。安静时段内全部延后。
- **合并**：短时间内的多条摘要项合成一条。
- **重试**：渠道发送失败时重试，记录最终状态。
- **留底**：已送达的消息就是 8.2 里"已经告诉过你的"来源。
- **净化**：去掉远程图片。图片地址可以夹带数据，是一条外泄通道。

## 14.3 从安静开始

默认上限定得很低。Agent 的系统提示词里写明：保持安静是正常结果，只有你需要现在知道的事才用即时通知。

每条通知带"有用""没必要"两个按钮。反馈作为事件回到 Agent，并进入夜间整理。上限由你手动调高，Agent 不能自己调。

**发不发的判断要用评测来调**。准备一组二三十个"事件加背景"的用例，标注期望结果是即时、摘要还是安静。每次改提示词或换模型后跑一遍。这是整个项目里最接近"产品质量"的一项指标。

# 16. 浏览器

- 浏览器在独立的容器里，有自己的配置目录，隔离区读不到。
- 隔离区通过宿主接口里的浏览器代理人操控它，只有几个动作：打开地址、取页面的无障碍树、点击某个节点、在某个节点输入、截图。
- 不提供"在页面里执行脚本"，不暴露调试接口。
- 登录由你完成：宿主给你一个远程查看页面，你接管浏览器手动登录，密码不经过隔离区。
- 需要你登录时，运行以"延迟"结束，和审批走同一套机制：你登录完，一条事件把它叫回来。

**权限**。不判断"这次点击危不危险"，而是看点击之后浏览器实际发出的请求。浏览器的流量同样经过出网代理和裁决者。

| 浏览器发出的请求 | 判定 |
| --- | --- |
| 导航和资源加载（GET） | 按公网规则，页面内的链接都算"见过" |
| 对未登录站点的非 GET | 询问，展示表单字段 |
| 对已登录站点的非 GET | 询问，除非该站点有档案或授权 |

很多网站用 POST 做查询，所以第三行仍会产生不少审批。办法是给常用站点写档案，把查询类请求标成 `read`。

# 17. 多角色

## 17.1 模型

一个角色是一份角色说明加一套自己的记忆。参照 Grok Bot 公开的产品设计：

| 各角色独有 | 所有角色共用 |
| --- | --- |
| 角色说明、记忆、进度文件、会话、例行任务 | 收件箱、电脑、工具、技能、账号连接、授权 |

角色不是进程。它只是工作进程启动运行时带上的一个参数，决定加载哪份角色说明和哪个记忆目录。

## 17.2 协作

- 你可以点名对某个角色说话；没点名的交给默认的协调者角色。
- 角色用 `handoff` 把任务交给另一个角色。这会在收件箱里产生一条事件，由目标角色的下一次运行处理。
- 因为只有一个工作进程，角色之间是轮流干活，不是同时干活。这避免了多个角色同时改同一份文件。
- 两个上限防止互相踢皮球：一条用户消息引发的交接不超过 5 跳；一个任务的总花费有上限。

## 17.3 角色不是安全边界

同一个隔离区里的角色共用一套替身令牌和一个文件系统。给它们设不同的权限没有意义。授权是发给隔离区的。

分角色的目的是分开上下文和记忆，让每个角色专注一类事。将来需要权限不同或需要并行的角色时，做法是给它单独的隔离区和单独的收件箱。

# 20. 实施路线

九步，每步结束都能用。前八步用容器驱动，第 9 步把电脑换成 microVM。从第 3 步起每步的验收都包含对抗测试：把隔离区里的程序换成你自己写的恶意脚本，让它拿着能拿到的一切去攻击。这样测的是架构，结果是确定的。

## 第 1 步：一次运行

内容：收件箱（表、接收端、工作进程）、会话记录、模型代理、电脑的驱动接口与容器实现（含加固）、运行程序、最简的发件（直接发回复）、Telegram。

学到：Agent 不是一个进程而是一连串运行；收件箱作为事实来源。

验收：
- 能对话。没有消息时，隔离区里没有任何 Agent 进程。
- 连发三条消息，只产生一次运行，三条都被看到。
- 同一条消息重复投递两次，只处理一次。
- 运行到一半杀掉工作进程，重启后事件被重新处理，你不会收到两次回复。
- 隔离区里找不到模型密钥；除三个出口外任何地址都连不上。

## 第 2 步：电脑与记忆

内容：本地工具、主目录布局、指令与索引的加载、进度文件的约定、压缩与换新会话、`recall`、文件收发、主目录快照。

学到：上下文工程；"只存查不回来的"在实践中意味着什么。

验收：
- 场景 S1、S2 跑通。
- 一个需要三次运行才能完成的任务：每次运行后杀掉并清空会话，下一次仍能凭进度文件接上。
- 故意让 Agent 把记忆改坏，能从快照恢复。

## 第 3 步：网络出口

内容：出网代理、内网拦截、基础设施白名单、搜索服务、"见过的地址"规则、裁决者、五种授权范围、延迟审批的完整闭环。

学到：整个设计的核心。裁决者、能力凭据、运行如何为了等你而结束再回来。

验收：
- 场景 S3 跑通，全程不需要审批。
- 触发一次审批后不理它，期间 Agent 能正常处理别的消息；之后批准，原任务自动接上。
- 对抗测试：恶意脚本尝试把金丝雀文件的内容发到你控制的外部服务器，包括拼进查询参数、放进 POST、放进请求头、经重定向、经域名解析到内网。全部被拦或进入审批。
- 恶意脚本无法看到审批内容，无法让一个审批变成已批准。

## 第 4 步：凭证与服务档案

内容：凭证服务、替身令牌与主机绑定、服务档案、第一个服务（邮箱）、响应过滤、注入检测。

学到：凭证替身；声明式的权限描述；响应改写。

验收：
- 场景 S4 跑通，审批里显示的收件人和正文与实际发出的一致。
- 对抗测试：恶意脚本把替身令牌发往非绑定主机，对方收到的不是真凭证；尝试让接口回显凭证，拿不到；未经批准发信为 0。
- 给自己发一封带验证码的邮件，Agent 读到的正文里验证码已被抹掉。

## 第 5 步：时间与发件

内容：定时器库、调度器、跟进与日程、前置检查、Webhook 接收与关联键、发件箱与分发器、通知反馈、夜间整理、发不发的评测集。

学到：常驻 Agent 区别于聊天机器人的全部内容；"值不值得说"有多难判断。

验收：
- 场景 S5、S6、S7 跑通，连续运行一周。
- 一周内没有事件的时段，模型调用次数为 0。
- 带前置检查的盯价日程，在价格未变的日子里不产生运行。
- 宿主停机一小时后启动，错过的跟进被补上，错过的日程每个只补一次。
- 评测集上"该安静时安静"的准确率达到你设定的线；一周内你标记"没必要"的即时通知少于三分之一。

## 第 6 步：自我扩展

内容：`connection_request`、`profile_propose` 与档案审阅界面、技能、例行任务。

学到：这一代 Agent 和上一代的主要能力差别，以及它为什么必须建立在出口之上。

验收：
- 场景 S8 跑通：从一句话到能查工单，你只做了两件事（填密钥、确认档案）。
- 对抗测试：恶意脚本提交一份把删除标成 `read` 的档案，审阅界面明确标出；未确认前不生效。

## 第 7 步：浏览器

内容：浏览器容器、代理人、无障碍树、接管登录、浏览器流量接入裁决者。

验收：场景 S9 跑通；隔离区读不到浏览器的配置目录；已登录站点上的提交类请求全部经过裁决。

## 第 8 步：多角色

内容：角色的定义与各自的记忆、点名与协调者、交接、跳数与预算上限。

验收：场景 S10 跑通；两个角色互相无限交接的情况被上限终止并报告给你。

## 第 9 步：把电脑换成 microVM

可以在第 5 步之后的任何时候做。它只替换驱动，上层代码不动。

内容：客户机内核与根文件系统镜像、主目录盘与核心盘、tap 网络与宿主侧规则、客户机代理程序与 vsock、经监禁程序启动、挂起与恢复、`keep_awake`、恢复后对时。

学到：硬件虚拟化的隔离是怎么搭起来的；状态快照；为什么这一代产品都把边界放在虚拟机上。

验收：
- 换驱动后，前面各步的验收测试不改一行全部通过。
- 场景 S12：空闲 10 分钟后宿主上没有监视器进程，电脑占用的内存和 CPU 为 0；发一条消息，电脑恢复并开始运行。
- 挂起前启动的后台进程在恢复后继续执行，电脑里的时间是对的。
- 调用 `keep_awake` 后，一个 30 分钟的脚本不被冻住；超过上限后照常挂起。
- 对抗测试：给恶意脚本客户机里的 root，除三个出口外仍然什么都够不着。
- 在挂起产生的状态文件里搜索模型密钥和测试用的真凭证，命中为 0。
- 量出冷启动耗时、恢复耗时、状态文件大小，写进文档。

# 21. 和参照的对应关系

除 Muse 外，各产品的内部实现没有公开，只能对应到可见的产品行为。

| 本文档 | 对应 | 主要差别 |
| --- | --- | --- |
| 运行周期、收件箱、定时器、发件箱 | Anthropic 文章的对应部件 | 基本照搬；多角色共用一个收件箱是本文档的选择 |
| 记忆布局、夜间整理 | 同上，文章称后者为 dreaming | "已告知"改由宿主从发件箱提供，不让 Agent 自己记 |
| 延迟审批 | 文章的延迟工具调用 | 文章在工具调用层延迟；本文档在网络出口处延迟 |
| 电脑加宿主侧 | Muse 的运行时隔间加隔间外的服务 | Muse 是两层边界，把守服务在用户的虚拟机内；本文档合成一层，把守者在宿主上 |
| 电脑用 microVM | Grok Bot 每用户一台常驻的 Firecracker microVM；Muse 每用户一台虚拟机 | 单机单用户；Grok Bot 是否做挂起恢复，官方文档没有写 |
| 裁决者 | Muse 的 Sentinel；文章提到的分类器自动审查 | 本文档完全基于规则 |
| 替身令牌 | Muse 的凭证替身；文章的凭证代理 | 相同思路 |
| 公网规则 | Muse 的染污出网 | Muse 在内核层逐进程追踪；本文档假设始终已攻破，加"见过的地址" |
| 浏览器代理人 | Muse 的浏览器子 Agent 与接管 | 没有页面内容分类器 |
| 多角色 | Grok Bot 的 Bot、群聊、例行任务 | 轮流运行，不并行 |
| Agent 自己的邮箱、电话、钱包 | Manus Cue | 未做 |

# 22. 已知的洞

| 洞 | 说明 | 现状 |
| --- | --- | --- |
| 低带宽外泄 | 搜索词本身、在多个"见过的地址"之间做选择、请求的时间间隔，都能携带少量信息 | 接受。出网日志可审计 |
| 经已连接服务外泄 | 把私有数据写进别人看得到的地方 | 属于 `send`，默认询问 |
| 长期授权被滥用 | 被攻破的 Agent 在授权范围内可以随意行动 | 约束写窄；注入检测命中时暂停；一键重置 |
| 定时器被滥用 | 被攻破的 Agent 给自己设一堆定时器反复醒来烧钱 | 数量与频率上限；每日花费上限；重置时清空 |
| 审批疲劳 | 审批多了人会不看就点 | 档案和授权范围；没有彻底解法 |
| 社会工程 | Agent 在消息里劝你"请批准接下来的请求" | 审批内容由裁决者生成；自述单独标为不可信 |
| 一次只有一个运行 | 一个长运行会让后面的事件等着 | 你的消息可以让后台运行让路；运行有时限 |
| 容器共享内核 | 前八步用容器驱动，容器逃逸即全盘失守 | 第 9 步换成 microVM 后消除；之前可先换 gVisor |
| 挂起冻住后台进程 | 没有调用 `keep_awake` 的长任务会被冻住，网络连接在恢复后失效 | 系统提示词里说明；配合跟进定时器 |
| 宿主是唯一的可信基座 | 把守者都在宿主上，宿主被攻破则全盘失守 | 自托管单用户的前提；多租户时需要 Muse 那样的两层 |
| 宿主侧是单进程 | 一处漏洞波及全部 | 之后可拆分并互相隔离 |
| 解密 HTTPS 的副作用 | 做了证书固定的客户端会失败 | 逐个处理 |
| 模型提供方可见内容 | 邮件、文件会进入模型请求 | 不在范围内；可换本地模型 |

# 23. 之后可以往哪长

| 方向 | 做法 |
| --- | --- |
| 并行 | 每个需要并行的角色一个收件箱、一个工作进程、一个隔离区 |
| 更多事件来源 | 邮箱和日历的推送通知，替代定时去查 |
| Agent 自己的身份 | 给它一个专用邮箱作为单独的连接，以它自己的名义发信，默认策略可以更宽 |
| 支付 | 由宿主申请绑定商户、金额、时间窗的一次性卡号，每次结账都审批 |
| 内核层数据流追踪 | 用 eBPF 逐进程标记，替换"假设始终已攻破"，换取更少的审批 |
| 用模型辅助裁决 | 对规则判不了的请求，用分类模型给出风险评估供你参考 |
| 更强的隔离 | 宿主侧的把守服务拆成互相隔离的进程；状态文件和主目录盘加密 |
| 多租户 | 每个用户一台 microVM 作外层边界，把守服务移进用户的虚拟机内，另加内层运行区 |
